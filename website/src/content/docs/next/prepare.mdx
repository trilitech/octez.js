---
title: Prepare Provider
---

Before operations are _forged_, _signed_, and then _injected_, they first need to go through a _prepare_ step.

In octez.js, the act of preparing an operation is to create the Operation Object and the counter in one single object that we name `PreparedOperation`.

An example of `PreparedOperation` object for a `ballot` operation looks something like this:
```typescript
{
  opOb: {
    branch: 'test_block_hash',
    contents: [
      {
        kind: 'ballot',
        ballot: 'yay',
        period: 103,
        proposal: 'PtKathmankSpLLDALzWw7CGD2j2MtyveTwboEYokqUCP4a1LxMg',
      },
    ],
    protocol: 'test_protocol',
  },
  counter: 0,
}
```

Having access to the `PreparedOperation` object offers a few benefits, a few of them being:
- The ability to retrieve information about the operation before injecting (operation hash, etc)
- The ability to simulate an operation before injecting

The `PrepareProvider` class affords extension and control to users when preparing operations while also promoting modularity in octez.js as a design principle.

## Detached signing

Sometimes the key that signs an operation lives somewhere else: a hardware device, a signing
service, or an approval step run by another person. `Tezos.prepareFor` prepares and estimates
operations from the account's **public** identity only, and leaves signing to that external
party:

```js
const workflow = Tezos.prepareFor({
  pkh: 'tz1...',
  publicKey: 'edpk...', // optional for an account that is already revealed
  // proof: 'BLsig...', // BLS proof of possession, needed to reveal a tz4 account
});

const prepared = await workflow.prepare.transaction({ to: 'tz1...', amount: 1 });
const signable = await workflow.toSignable(prepared);

// ... send `signable` to the external signer, get back a Base58Check signature ...

const signed = workflow.attachSignature(signable, signature);
const op = await workflow.inject(signed);
await op.confirmation();
```

`workflow.prepare` and `workflow.estimate` support transactions, delegations, originations,
reveals, contract calls, and batches of transactions, delegations and originations. Every
operation must come from the identity's `pkh`. A reveal must use the identity's public key and,
for a tz4 account, its proof.

### What the external signer signs

`toSignable` forges the operation and returns a frozen snapshot of it:

- `unsignedBytes`: the forged operation;
- `watermarkedBytes`: `03` followed by the forged bytes;
- `blake2bDigest`: the 32-byte Blake2b hash of the watermarked bytes;
- `scheme` and `signingInput`: BLS (tz4) keys sign `watermarkedBytes`. Ed25519, secp256k1,
  P-256 and ML-DSA-44 keys sign `blake2bDigest`.

`attachSignature` takes the Base58Check signature for the identity's scheme. The generic `sig`
prefix is also accepted for the 64-byte schemes. When the identity includes a public key, the
signature is checked against the watermarked bytes before anything is sent. The signed bytes
are exactly the approved bytes, followed by the signature: BLS signatures are prefixed with
`ff03` and ML-DSA-44 signatures with `ff04`, as Octez does.

The snapshot can't be changed after `toSignable`: editing `prepared` afterwards has no effect.
Snapshots only work with the workflow that created them, in the same process.

### Injection and retries

`inject` preapplies the signed operation before injecting it. If the node reports an error, or
any operation result isn't `applied`, it throws (`TezosOperationError` or
`TezosPreapplyFailureError`) and nothing is injected. On success it returns the usual `Operation`
handle, so you can wait for confirmations as with any other operation.

`inject` runs only once for a given signed operation. Calling it again with the same `signed`
object returns the same promise, so a retry after a timeout can't inject the operation twice.
To submit after a failure, prepare, sign and attach again.

### Providers and operation lifetime

`prepareFor` captures the toolkit's RPC client, configuration and custom providers when it is
called. Later calls to `setProvider` or `setRpcProvider` don't affect a workflow that already
exists. Call `prepareFor` again to use the new providers.

A prepared operation is anchored to a recent block (its branch, `head~2` when it was prepared).
The protocol accepts it only while that block is among the last `max_operations_ttl` blocks, so
an operation that waits too long for its signature is rejected at preapplication. In that case,
prepare and sign it again.

## Usage example

### Individual Operations
The `PrepareProvider` is accessible via the `TezosToolkit` class:
```typescript
// const Tezos = new TezosToolkit('RPC_ENDPOINT');

const prepared = await Tezos.prepare.transaction({
  to: 'tz1QZ6KY7d3BuZDT1d19dUxoQrtFPN2QJ3hn',
  amount: 5
});
```

Let's break that transaction prepare call down.

The interface of the `transaction` member method is as follows:
```typescript
transaction(params: TransferParams , source?: string): Promise<PreparedOperation>;
```

- `params` is the Transaction operation parameters. In this case, the required properties are `to` and `amount`.
- `source` is the source public key hash if you do wish to override the source. This parameter is optional by design. If you do not wish to override it, the source will be grabbed from the `Context`.

### Batch Operations
`PrepareProvider` also has support for batch operations:
```typescript
const prepared = await Tezos.prepare.batch([
  {
    kind: OpKind.TRANSACTION,
    to: 'tz1QZ6KY7d3BuZDT1d19dUxoQrtFPN2QJ3hn',
    amount: 2,
  },
  {
    kind: OpKind.TRANSACTION,
    to: 'tz1QZ6KY7d3BuZDT1d19dUxoQrtFPN2QJ3hn',
    amount: 2,
  },
]);
```
The parameters for each object in the array are the required parameters for each respective operation, with the added `kind` property that denotes the operation kind. Users can also utilize `OpKind` which is an enum that holds operation kind values.

### Contract Calls
Users are also able to utilize the `PrepareProvider` to prepare contract calls:
```typescript
const contractAbs = await Tezos.contract.at(contractAddress);
const method = await contractAbs.methodsObject.increment(1);
const prepared = await Tezos.prepare.contractCall(method);
```

## Conversion methods

We've also added a couple utility methods to convert a `PreparedOperation` into objects that can be consumed by the `forger` as well as the `preapplyOperations` method.

### `toPreapply()`
The `toPreapply()` method converts a `PreparedOperation` object into an entity that is consumable by the `preapplyOperations()` method in the RPC package (i.e. `PreapplyParams` type object).

#### Example
```typescript
const preparedTransferOp = await Tezos.prepare.transaction({
    amount: 1,
    to: 'tz1ZfrERcALBwmAqwonRXYVQBDT9BjNjBHJu'
});
const params = await Tezos.prepare.toPreapply(preparedTransferOp);
const preapplyOp = await Tezos.rpc.preapplyOperations(params);
```

### `toForge()`
The `toForge()` method converts a `PreparedOperation` into an object that can be passed into the `forge` method (i.e. `ForgeParams` type object)

#### Example

```typescript
const preparedTransfer = await Tezos.prepare.transaction({
  amount: 1,
  to: 'tz1ZfrERcALBwmAqwonRXYVQBDT9BjNjBHJu'
});
const params = Tezos.prepare.toForge(preparedTransfer);
const forgedBytes = await forger.forge(params);
```
