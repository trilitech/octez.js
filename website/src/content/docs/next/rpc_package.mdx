octez.js RPC Package Documentation

## Description

You can use the RPC client package to query the RPC API of your chosen node. The higher-level [`@tezos-x/octez.js`](https://octez-js.tezos.com/typedoc/modules/_tezos-x_octez.js.html) package builds on this RPC package, in general, you won't need to use this package directly, but it is available for use should you want some specific data and bypass the higher-level abstractions in octez.js.

Methods in the RPC package map one-to-one to the corresponding Tezos RPC API endpoints. All responses from the RPC are returns with TypeScript types. It doesn't do any other parsing or compositions at this level.

## Examples

```js
// Initializing the RPC client

import { RpcClient } from '@tezos-x/octez.js-rpc';

const client = new RpcClient('https://rpc.shadownet.teztnets.com', 'NetXsqzbfFenSTS');
```

The `RpcClient` constructor takes the URL of the node you want to use and the chain ID.

```js
/* Fetching the spendable balance of an account
 * using the client set up above */

const balance = await client.getBalance('tz1VSUr8wwNhLAzempoch5d6hLRiTh8Cjcjb');
console.log('-- Balance:', balance.toNumber());
```

The balance is returned as a `BigNumber` and must be converted to a number to output it. Please note that the returned value is in mutez (micro ꜩ), so if you need the balance in ꜩ, you can divide it by 1000000.

```js
// gets head block
const block = await client.getBlock();
console.log('-- Head block:', block);
```

You can use the RPC client to get the head block information.

```js
// gets head block hash
const blockHash = await client.getBlockHash();
console.log('-- Head block hash:', blockHash);
```

If it is the head block hash you are looking for, you can easily get it with the `getBlockHash` method.

```js
// gets constants
const constants = await client.getConstants();
console.log('-- Constants:', constants);
```

This method returns some blockchain constants pertaining for example to the gas limits or the block information.

```js
// gets contract
const contractExample = 'KT1J34ANCFtpnFX26djxvQRNytgKh6UJrCTN';
const contract = await client.getContract(contractExample);
console.log('-- Contract:', contract);
```

This method returns the balance of the contract, the code, and the storage.

```js
// gets contract entrypoints
const entrypoints = await client.getEntrypoints(contractExample);
console.log('-- Entrypoints:', entrypoints);
```

You can also get a list of the contract entry points as an object whose keys are the entry point names and whose values are the expected parameters in JSON format.

```js
// gets contract script
const script = await client.getScript(contractExample);
console.log('-- Contract script:', script);
```

The `getScript` method returns the contract's script as a 3 key/value pair object: a key for the parameter, a key for the storage, and a key for the code.

```js
// gets contract storage
const storage = await client.getStorage(contractExample);
console.log('-- Contract storage:', storage);
```

You also have access to the storage of the contract using the `getStorage` method.

```js
// packs data
const packedData = await client.packData({ data: { string: 'test' }, type: { prim: 'string' } });
console.log('-- Packed data:', packedData);
```

You can simulate the `PACK` instruction from Michelson with the `packData` method.

This function will execute Tzip4 views normally referred to as 'Lambda Views'. You can learn more about Tzip4 [here](https://gitlab.com/tezos/tzip/-/blob/master/proposals/tzip-4/tzip-4.md#view-entrypoints)
```js
// runs view
const view = await client.runView({
  contract: 'contractAddress',
  entrypoint: 'contractEntrypoint',
  chain_id: 'chainId',
  input: {
    string: 'testInput'
  }
});
```

### BLS helpers

Octez nodes expose shell RPCs under `/bls/` that work on BLS (tz4) keys and signatures. The node
does the cryptography, so you don't need a BLS library to check proofs or combine signatures:

```js
// Check a proof of possession: resolves to true or false
const valid = await client.checkProof({ public_key: 'BLpk...', proof: 'BLsig...' });

// Aggregate public keys; every proof is checked first.
// Resolves to { public_key, public_key_hash }, or null if a proof is invalid
const aggregate = await client.aggregatePublicKeys([
  { public_key: 'BLpk1...', proof: 'BLsig1...' },
  { public_key: 'BLpk2...', proof: 'BLsig2...' },
]);

// Aggregate signatures of the same message, given as unprefixed hex.
// Resolves to a Base58Check signature, or null if aggregation or verification fails
const signature = await client.aggregateSignatures({
  public_key: 'BLpk...',
  message: '00010203',
  signature_shares: ['BLsig1...', 'BLsig2...'],
});

// Rebuild a threshold signature from indexed shares (ids are signed 8-bit integers)
const rebuilt = await client.thresholdSignatures({
  public_key: 'BLpk...',
  message: '00010203',
  signature_shares: [
    { id: 1, signature: 'BLsig1...' },
    { id: 2, signature: 'BLsig2...' },
  ],
});
```

`aggregateProofs({ public_key, proofs })` combines the members' proofs over an aggregate key into
the proof for a native multisig account. See
[BLS proofs for a native multisig account](/docs/next/inmemory_signer#bls-proofs-for-a-native-multisig-account).

Invalid input is reported in the result (`false` or `null`), not as an exception. These calls
aren't cached by [`RpcClientCache`](/docs/next/rpc-cache#what-is-cached). `aggregateProofs` is
optional on `RpcClientInterface`: with a custom client that doesn't implement it,
`RpcClientCache` throws `UnsupportedActionError`.

If you implement `RpcClientInterface` yourself, `checkProof`, `aggregatePublicKeys`,
`aggregateSignatures` and `thresholdSignatures` are required members since octez.js 25.1.0:
add them, for example by forwarding to an `RpcClient`, or the implementation no longer compiles.
